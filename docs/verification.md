# 実機での確認事項と確認手段

このシステムには「実機でしか確かめられない前提」があります。
自動で確認できるものは `npm run doctor` に入れてあり、
残りは目と手で確かめる必要があります。この順に進めてください。

---

## どこで実行するか

**カメラを USB で挿したブリッジ機の、リポジトリを clone したディレクトリの中**です。
スマホ側では実行しません（スマホはブラウザで使うだけです）。

```bash
git clone https://github.com/YutoTsukuda/camera-control.git
cd camera-control
npm install
```

準備の詳細（Node 22 の導入、gphoto2 の導入、gvfs の停止）は
[usb-setup.md](usb-setup.md) を参照してください。

## 進め方

カメラを USB で接続した状態で、`camera-control` ディレクトリの中から:

```bash
npm run probe     # ① カメラが何を公開しているか調べる（結果を保存）
npm run doctor    # ② 設計の前提が成り立つか健診する
# ③ 以下の手動確認へ
```

`probe` は「何が読めるか」、`doctor` は「前提が成り立つか」を調べます。役割が違うので両方実行してください。

## 自動確認（`npm run doctor`）

| # | 確認事項 | なぜ必要か |
|---|---|---|
| 1 | gphoto2 が使えるか | 全機能の前提 |
| 2 | カメラを検出できるか | USB接続モードの設定漏れが最頻出 |
| 3 | カメラを占有できるか | Linux では gvfs が先に掴む問題が起きる |
| 4 | 設定ツリーを取得できるか | 項目数が極端に少ない＝テザー撮影モードに入りきっていない |
| 5 | 出力書式をパーサが解釈できているか | gphoto2 の版差（END 区切りの有無）を吸収できているか |
| 6 | **露出系が公開されているか** | 絞り/SS/ISO/露出補正。**これが無いと成立しない** |
| 7 | 絵作り系が公開されているか | フィルムシミュレーション等 |
| 8 | 光の調整・色のバランスが公開されているか | トーンカーブ、WBシフト、色温度 |
| 9 | 選択肢の表記を数値として解釈できているか | `f/2.8` `1/250` `+1` の表記が想定と合っているか |
| 10 | 列挙値をすべて照合できているか | フィルムシミュレーションの取り違えを防ぐ |
| 11 | **複数項目を1プロセスでまとめて読めるか** | 状態取得の設計前提 |
| 12 | **複数項目を1プロセスでまとめて書けるか** | 一括適用の設計前提。ここが崩れると設計変更が要る |
| 13 | 書いた値が実際に反映されるか | `--roundtrip` で実施。書き込み成功と実際の変更は別物 |
| 15 | Claude API への疎通 | `--ai` で実施。構造化出力が返るか |

```bash
npm run doctor                  # 読み取り ＋ 非破壊の書き込み確認
npm run doctor -- --roundtrip   # 値を変えて読み戻す（実行後に元へ戻す）
npm run doctor -- --ai          # Claude API 疎通も確認
npm run doctor -- --read-only   # カメラへ一切書き込まない
```

**12 が NG（一括不可）だった場合は必ず知らせてください。** アダプタを
1 項目ずつ書き込む方式へ変更する必要があります。設計の中核前提なので、
ここだけは結果を確認したいです。

## 手動確認

自動化できない、あるいは自動化すると危険なものです。

### A. 物理ダイヤルの位置

X100VI は物理ダイヤルが優先されます。リモートから書いても、
ダイヤルがその位置にあると拒否されます。

| 設定したいもの | 必要な位置 |
|---|---|
| 絞り | 絞りリングを **A** |
| シャッター速度 | SSダイヤルを **A** |
| ISO | ISO を **A**（オート）または **C** |
| 露出補正 | 露出補正ダイヤルを **C** |

**確認手段**: 上の位置に合わせた状態と、合わせていない状態の両方で
`npm run doctor` を実行し、12 番の結果が変わるかを見る。
拒否される項目が「非対応」ではなく `failed` として個別に報告されれば正しい挙動です。

### B. カメラの表示が実際に変わるか

書き込みが成功しても、カメラ側が無視している可能性があります。

**確認手段**:
1. カメラの背面液晶を見える状態にする
2. `npm run doctor -- --roundtrip` を実行する
3. フィルムシミュレーション表示が一瞬変わって元に戻るのを目視する

液晶が変わらないのに 13 番が OK なら、読み戻しだけが通っていて
実際には反映されていません。その場合は知らせてください。

### C. 撮れた写真が提案どおりか

最終的な答え合わせです。設定が「カメラに入った」ことと
「写真に反映された」ことは別です。

**確認手段**:
```bash
# サーバを起動してスマホから提案 → 適用 → シャッターを切る
# 撮れた写真を取り込んで Exif を見る
exiftool -FNumber -ExposureTime -ISO -ExposureCompensation \
         -FilmMode -Saturation -Sharpness -WhiteBalance \
         -HighlightTone -ShadowTone DSCF####.JPG
```

`exiftool` が無ければ `sudo apt install libimage-exiftool-perl`。
提案画面に出ていた値と Exif が一致するかを見ます。
**ハイライトトーン／シャドウトーンは Exif に出るので、
光の調整が本当に効いているかはここで確定できます。**

### D. レリーズ

実際に 1 枚撮影されるため doctor では試しません。

**確認手段**: サーバ起動後、スマホの「シャッターを切る」を押す。
またはコマンドで:
```bash
gphoto2 --trigger-capture
```
カードに 1 枚記録されれば成功です（本システムは転送を待たない
`--trigger-capture` を使うので、画像はカメラに残ります）。

### E. スマホから使えるか

**確認手段**:
1. ブリッジ機で `HOST=0.0.0.0 npm start`
2. スマホで `http://<ブリッジ機のIP>:8080/?token=<ACCESS_TOKENの値>`
3. 接続 → 写真を撮る → 提案 → 適用 が通ることを確認
4. ブラウザメニューから「ホーム画面に追加」→ アプリとして起動できるか
5. トークンを外した URL でアクセスし、401 になることを確認（認証が効いているか）

### F. 提案の質

これは私には評価できません。実際に撮って判断してください。

**確認手段**: 性格の違う 5 シーンで提案を出し、自分の判断と比べる。

| シーン | 見るべき点 |
|---|---|
| 晴天の屋外で背景をぼかしたい | ND が入り、絞りが開放付近に残るか |
| 逆光の人物 | 露出補正がプラスに振れ、シャドウトーンがマイナスか |
| 薄暗い室内 | ISO の上げ方と、ブレ限界の置き方が妥当か |
| 夜景（三脚） | 絞りを開放に張り付けず、長秒で低感度を選ぶか |
| 蛍光灯下の料理 | WB とシフトの当て方が妥当か |

提案が外していた場合、**どのシーンで何がどう違ったか**を教えてください。
プロンプト（`src/ai/prompt.ts`）とルールベース（`src/ai/rules.ts`）を調整します。

### G. 応答時間

**確認手段**: スマホで「AIに設定を提案してもらう」を押してから
提案が出るまでと、「カメラに適用」を押してから完了までを測る。

| 区間 | 目安 |
|---|---|
| 写真の縮小・送信 | 1秒未満 |
| Claude の提案 | 5〜15秒（`AI_EFFORT=low` で短縮できる） |
| カメラへの適用 | 1〜3秒 |

適用が 5 秒を超える場合、一括適用が失敗して個別再試行に落ちています。
サーバのログに出るので確認してください。

### H. 長時間の安定性

**確認手段**: 接続したまま放置し、以下を試す。

1. カメラのオートパワーオフが働いた後にスマホから状態取得 →
   「未接続」に変わり、理由が通知されるか
2. カメラの電源を入れ直す → 再度「接続」で復帰するか
3. USB ケーブルを抜き差しする → 同上
4. 1時間放置後に提案 → 適用が通るか

カメラ側の設定で **オートパワーオフを長め（またはOFF）** にしておくと安定します。

### I. 設定変更の反映

**確認手段**: カメラ本体で設定を変えた後、`GPHOTO2_RESCAN=true` を付けて起動し、
`config/gphoto2-mapping.json` が更新されるか。
保存済みマッピングは接続のたびに再取得しないので、
カメラのファームウェア更新後などは一度 `npm run probe` をやり直してください。

## 結果の報告

うまくいかなかった場合、次を貼っていただければ原因を特定できます。

| 状況 | 貼るもの |
|---|---|
| どの段階でも | `npm run doctor` の出力全文 |
| 項目が「非対応」になる | `config/gphoto2-mapping-raw.txt`（設定ツリーの生出力） |
| 照合が間違っている | `npm run probe` の該当部分 |
| 書き込みが失敗する | サーバのログ（`--set-config` の行と、その直後のエラー） |
| 提案が外す | どのシーンで、提案値と、自分ならどうするか |

`config/gphoto2-mapping-raw.txt` は機体固有の情報なので `.gitignore` に入れてあります。
共有する場合はシリアル番号が含まれていないか一度確認してください。
