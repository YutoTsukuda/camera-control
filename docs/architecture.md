# 設計

## 課題設定

「AI にカメラ設定を決めさせる」で素直に作ると、モデルに設定一式を JSON で吐かせて
そのままカメラへ流す形になります。これは次の理由で現場では使えません。

1. **露出は算術の問題である。** 絞り・シャッター速度・ISO の関係は EV 式で一意に決まる。
   言語モデルにこれを毎回正確に解かせるのは、確率的な手段で決定論的な問題を解くことになる。
2. **機種固有の制約は暗黙知である。** X100VI のリーフシャッターは F2 で 1/1000 秒までしか切れない。
   DR400% は ISO500 以上を要求する。デジタルテレコンは RAW と排他。
   こうした条件を全部プロンプトに書いても、守られる保証はない。
3. **失敗のコストが非対称。** 変な絵作りは撮り直せるが、露出が 3 段外れた写真は戻らない。

## 責務分担

そこで、**AI にしかできないこと**と**計算で確実に解けること**を分けています。

```
         ┌──────────────────────────────────────────┐
写真+意図 │  Claude                                  │
────────▶│   ・光の向き/質/色を読む                  │
         │   ・撮影意図を汲む                        │
         │   ・優先軸を決める（exposurePlan）        │
         │   ・絵作りを選ぶ（look）                  │
         └───────────────┬──────────────────────────┘
                         │ Advice（構造化出力）
                         ▼
         ┌──────────────────────────────────────────┐
         │  露出ソルバ  domain/exposure.ts           │
         │   ・EV 式を解く                           │
         │   ・手ブレ/被写体ブレ限界を守る            │
         │   ・ND→電子シャッター→絞り込みで逃がす     │
         └───────────────┬──────────────────────────┘
                         ▼
         ┌──────────────────────────────────────────┐
         │  バリデータ  domain/validate.ts           │
         │   ・1/3段ラダーへ丸める                   │
         │   ・排他/依存関係を解く                   │
         │   ・変更理由を日本語で記録                │
         └───────────────┬──────────────────────────┘
                         ▼
                  ShootingSettings ──▶ カメラアダプタ
```

AI が返す `exposurePlan` は具体値ではなく**方針**です。

```ts
{
  preferredAperture: 2,      // 絵作り上の希望F値
  slowestShutterSec: 1/125,  // これより遅いとブレる
  maxIso: 6400,              // ここまでなら許容
  exposureCompensation: 1,   // 逆光なので +1EV
  preferredShutterType: 'MS',
  allowNd: true,             // 日中開放なのでND可
  allowStopDown: false,      // ボケが目的なので絞りたくない
}
```

ソルバはこの方針と実測 EV から、機構上あり得る組み合わせを探索します。
方針が両立しない明るさでは、優先順位（希望絞りを最後まで守る → ISO を低く保つ →
ブレ限界を守る）に従って妥協し、**妥協した内容をすべて `corrections` に残します**。

## corrections という設計判断

システムが勝手に値を変えたとき、それを黙って行うのは道具として不誠実です。
本システムは変更をすべて記録し、UI に日本語で表示します。

```
・NDフィルター: 明るすぎて F2 では 1/1000 でも露出オーバーになるため、内蔵ND（4段）を使用します。
・ISO感度: DR400 は ISO 500 以上でのみ選択できるため、ISO を 500 に上げました。
・シャッター方式: F2 のメカニカルシャッター上限は 1/1000 です。1/8000 を実現するため電子シャッター併用に変更しました。
```

`severity` は 3 段階です。

- `note` — 値は変えていない補足（「A モードでは SS はカメラが決めます」）
- `info` — 値を変えたが撮影結果への影響は小さい
- `warn` — 意図どおりに撮れない可能性がある

`note` が値を変えないことには実装上の意味があります。バリデータは**冪等**であり、
検証済みの設定を再検証しても値が変わってはいけない。これはテストで固定しています。

## フォールバックの設計

撮影現場では「提案が出ない」が最悪の結果です。したがって:

- Claude が失敗したら（タイムアウト、圏外、レート制限、認証エラー）**必ず**ルールベースへ落ちる
- ルールベースは Claude と同じ `Advice` 型を返すので、下流のパイプラインは完全に共通
- 落ちた理由は `fallbackReason` として UI に表示する（黙って質を下げない）

さらに、構造化出力のスキーマは `.catch()` で語彙外の値を安全な既定値へ落とします。
Anthropic の構造化出力は JSON Schema のサブセットを使うため、SDK は `enum` や
`min`/`max` をスキーマから外して説明文へ畳み込みます。つまり語彙の遵守は
ハードな保証ではありません。1 項目の逸脱で提案全体を捨てるのは損なので、
その項目だけ既定値へ落とします。

## プロンプトキャッシュ

システムプロンプトは `capabilities.ts` / `labels.ts` のテーブルから**決定論的に生成**しています。

- 仕様表を直せばプロンプトも自動追従する（二重管理をなくす）
- 生成結果がリクエスト間で完全に同一なので、prompt caching が効く

揮発する情報（撮影意図・測光値・写真）はキャッシュ境界より後ろのユーザーメッセージに置きます。
システムプロンプトにタイムスタンプを入れないことはテストで固定しています。

## カメラアダプタの抽象

上位層は接続方式を知りません。

| アダプタ | 用途 | 確度 |
|---|---|---|
| `mock` | 実機なしの開発・デモ | — |
| `ptpip` | Wi-Fi 直結 | 標準プロパティは高、独自プロパティは要検証 |
| `sdk-bridge` | 公式 Camera Remote SDK をラップした別プロセスへ委譲 | 高（本番推奨） |

`mock` は単なるスタブではなく、測光値・値の拒否・通信遅延を再現します。
実機で起きる失敗の多くはここで先に再現できます。

## なぜブリッジサーバが要るか

スマホのブラウザは生の TCP ソケットを開けないため、カメラの PTP/IP を直接叩けません。
また Claude の API キーを端末に置きたくありません。したがって間に 1 プロセス挟みます。

ネットワーク構成の選択肢は [hardware-setup.md](hardware-setup.md) を参照してください。
